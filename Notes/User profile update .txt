**Execution Plan**

This approach is cleaner, and yes, it can be done without breaking existing functionality if we keep it tightly scoped to the current employee `PUT` flow and make the AuthNexus sync non-blocking.

1. Verify the permission model first.
   Before we build anything, confirm that the logged-in admin’s existing bearer token can call the AuthNexus profile update endpoint.
   The one thing this plan depends on is: the token already sent to your backend must also be accepted by `PUT` or `PATCH /api/admin/users/{user_id}/profile` on AuthNexus.
   If that test returns `403`, we stop and fall back to the service-account design.
   If it returns `200`, this is the best path.

2. Confirm the exact AuthNexus API contract.
   Lock down:
   the exact method: `PUT` vs `PATCH`
   the exact path
   whether `org_id` is required
   the exact JSON body fields
   the expected auth header format
   This avoids building around the wrong endpoint shape.

3. Keep the current backend route as the only integration point.
   Reuse the existing `PUT /api/v1/employees/{id}` route in [api_v1_employees.py](/d:/AMS/assetmanager/Server/routers/api_v1_employees.py:272).
   We do not add new frontend calls, new routes, or new auth flows.

4. Capture the caller’s bearer token inside the existing request.
   In the employee update route, read the incoming `Authorization` header from the current request context.
   That token becomes the forwarded AuthNexus token.
   No new `.env` secrets, no token cache, no service login flow.

5. Preserve the current local DB update as the primary action.
   The route should continue to:
   validate the request
   update the local `employees` row
   return the same success envelope it already returns
   This keeps existing frontend behavior stable.

6. Only trigger AuthNexus sync when `name` or `email` changed.
   Compare the employee row before and after the local update.
   If only department, role, or `is_active` changed, skip AuthNexus entirely.
   That keeps the new integration narrow and reduces risk.

7. Skip safely when no AuthNexus-linked user exists.
   If `auth_user_id` is null on the employee row, do nothing beyond the local DB update.
   That protects existing records that are not linked yet.

8. Add a tiny AuthNexus forwarding client, not a new auth system.
   Create a focused service module that only:
   accepts a bearer token
   builds the AuthNexus profile payload from local `name` and `email`
   calls the AuthNexus user-profile endpoint
   No login logic, no refresh logic, no persistent credentials.

9. Make AuthNexus sync best-effort, not request-breaking.
   If AuthNexus returns timeout, 5xx, or temporary failure:
   local DB update still succeeds
   current API response stays `200`
   backend logs a warning with enough detail to investigate
   This is the key guardrail that prevents regressions in the current employee edit feature.

10. Keep the frontend untouched.
   No changes needed in:
   [EmployeeForm.tsx](/d:/AMS/assetmanager/Client/src/components/form/EmployeeForm.tsx:38)
   [employeeService.ts](/d:/AMS/assetmanager/Client/src/services/employeeService.ts:64)
   [api.ts](/d:/AMS/assetmanager/Client/src/api.ts:588)
   The frontend already sends `name` and `email`; the backend can transparently dual-write.

11. Verify the non-regression cases explicitly.
   After implementation, test:
   edit department only: local DB updates, no AuthNexus call
   edit role only: local DB updates, no AuthNexus call
   edit status only: local DB updates, no AuthNexus call
   edit name: local DB updates, AuthNexus sync runs
   edit email: local DB updates, AuthNexus sync runs
   `auth_user_id` missing: local DB updates, AuthNexus skipped
   AuthNexus denied or down: local DB updates still succeed

**Risk Summary**

This plan is lower risk than the `.env` service-account version because it does not add secrets, token caching, or a second authentication path. The only real dependency is whether the current admin token is authorized by AuthNexus for profile edits. If that answer is yes, this is the safest implementation path for preserving existing functionality.

**Recommended next move**

Test the logged-in admin token against the AuthNexus profile-update endpoint first. That is the decision gate for the whole design. If it passes, we can turn this into a file-by-file implementation plan immediately.
